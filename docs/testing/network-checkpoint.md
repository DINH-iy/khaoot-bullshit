## Connection model

All devices use the same public HTTPS origin with secure real-time connections. Players can be on home Wi-Fi, another Wi-Fi network or mobile data; there is no LAN-only assumption. The backend and PostgreSQL remain on the host computer for this rehearsal; only the built browser app/API/socket server is reachable through the temporary tunnel. PostgreSQL stays on localhost. A final home deployment needs a stable public hostname, HTTPS and a durable tunnel/reverse-proxy setup.

Use Cloudflare Quick Tunnel only for temporary testing. Its URL changes on restart, has no uptime guarantee and has a 200 in-flight request limit. It supports this WebSocket/polling test path; it is not production hosting or proof of final capacity. [Quick Tunnel documentation](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), [WebSocket support](https://developers.cloudflare.com/network/websockets/)

## Verified access

- Normal room creation verifies an OIDC API token and `games:write`, maps issuer+subject to an existing creator, checks version ownership, and issues a short-lived room host credential. Session/command UUIDs make retries return the same room/credential. Live provider sign-in UI/account setup is still deferred; cryptographic verification is tested with a local test issuer.
- Rehearsal host access is explicitly generated by the owner-run local CLI, scoped to one REHEARSAL session, expires in one hour, and is rejected in production. There is no unauthenticated create-host endpoint or implicit development login bypass.
- Local owner hosting (added 12 November 2026) lets the owner open rooms from a browser menu. It requires the generated `LOCAL_OWNER_TOKEN`, delivered once in a private link and then kept in an HttpOnly cookie; configuration refuses that token in production, and the rooms it creates use the same production-rejected rehearsal grants, valid for eight hours.
- Guest admission uses the public room code plus a private random join ID, then issues an opaque four-hour credential. Retry of the same join recovers the same identity/credential; repeating a nickname cannot take another player's identity. Store only token hashes in PostgreSQL. A separate server secret derives retry-safe join tokens and must survive backend restarts.
- Browser credentials are HttpOnly, SameSite=Strict and Secure on HTTPS. Host/player cookies are session-scoped; display credentials use a separate cookie so opening a display tab does not replace host access. Host/display bootstrap links use a URL fragment, which is removed before requests; only the token-claim body contains it. Do not share host/display links as player invitations.
- Every socket action rechecks current credentials, expiry, revocation and room membership. Commands also recheck credential proofs inside their locked transaction. Host revocation disconnects that player's current sockets. Display access cannot issue commands.
- HTTP requests require the application request header and trusted origin. Socket handshakes validate the exact configured origin; same-origin polling GETs without Origin use the expected Host check. Credentials remain mandatory regardless of headers. Payloads, event rates, duplicate connections, pending work and retry delays are bounded.

Public room APIs: join, claim, create (OIDC only), read snapshot, mint display access (host only), revoke player (host only), and logout. Socket events: room.sync, room.command, room.receipt and room.heartbeat. Clients never submit their own trusted role or player ID as authentication. Unauthorized/error replies and logs omit tokens, answers, names and query strings.

## Seat takeover on another phone (added 12 November 2026)

- `GET /api/rooms/seats/:roomCode` lists seats with no phone connected to this server process (single-backend presence). Removed players are never listed.
- `POST /api/rooms/reclaim` with a phone-generated request ID asks for a seat; repeating it checks on the request. The new credential is derived from that ID, so retries return the same access.
- The room setting `reclaimApproval` (host, `POST /api/rooms/:id/settings`, off by default) decides whether the host must approve (`POST /api/rooms/:id/seat-requests`). Requests expire after ten minutes; at most 20 wait at once. The host may approve even if the old phone has come back, which disconnects it.
- Approval revokes every earlier credential of that seat and disconnects its sockets. Answers, scores and the player ID are unchanged.
- With approval off, anyone holding the room code can take a seat whose phone is momentarily disconnected. That is the owner's deliberate default for friends; the host can switch approval on at any moment.
- Pending requests are stored in the room's database row, so they survive a restart; presence does not, so after a restart every seat looks free until phones reconnect.

## State and recovery

Accepted commands use the existing atomic command/score/audit/outbox transaction. The socket acknowledgement follows commit. Pending UI actions retain their original command ID/stage locally; after reconnection, the phone asks for its own receipt and reloads safe state before retrying an eligible unsaved answer. Retry cannot award points twice. Local retention can fail; it is never called server confirmation.

The publisher emits bounded batches of safe revision invalidations and player-specific receipts from the durable outbox, then records publication. Publication is not proof that every client received an event. Reconnection, visibility/online changes and a periodic sync reload current authorized state; duplicate/out-of-order invalidations cannot replace a newer snapshot. A lost acknowledgement can be resolved through room.receipt without resubmitting into another stage.

On backend startup, previously running credentialed rooms are paused through normal audited commands before accepting room traffic. The host reviews/resumes; saved entries and points remain. This startup recovery currently assumes a single authoritative backend; a multi-instance deployment needs leases/room ownership. Socket connection recovery is not trusted as durable storage.

The test screen measures round-trip time through a credential check and saved-command confirmation separately. p95 is calculated over at most the latest 60 round-trip samples and displays the sample count. It is not pure network ping, a large-sample benchmark or a fairness guarantee. Runtime presence is approximate; durable player identity survives socket replacement.

Initial safety budgets: 16 KiB messages, three sockets per credential, 512 transport connections per backend, 180 events/minute per credential, shared-IP HTTP/join/connect limits, bounded database work and a 100-event publisher batch. These are hosting controls, not a game-definition player cap. Tune against real shared-network and reconnect-storm measurements before release. Identity-free admission can still be abused; this rehearsal is not a completed public abuse-protection service.

## Run the rehearsal

Use Node 24, the existing local development database and reviewed migrations:

```sh
npm ci
npm run db:up
npm run db:migrate:deploy
npm run build
npm run network:prepare
npm run network:public
```

`network:prepare` requires the local `_dev` database, generates the missing ignored room secret without printing it, and creates a prepared rehearsal room. It writes short-lived host access under ignored `.local/` with restricted file permissions. It does not change firewall/router settings or expose PostgreSQL.

Install the official [cloudflared executable](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/) in `.local/tools/cloudflared`, or set `CLOUDFLARED_BIN` to its installed path. Use the build for your OS/architecture; never copy the Mac binary to the Pi. The public launcher serves built files, not the Vite development server. It starts an ephemeral outbound HTTPS tunnel and prints only the player URL/code. Closing the launcher ends the link. It does not create a permanent Cloudflare account/domain or production deployment.

While the launcher remains running, open the private host link from another terminal:

```sh
npm run network:host
```

The host opens on the same public HTTPS origin, claims its own credential and displays a player link. Open that player link on Android Chrome. Old cookies belong to the old temporary hostname after a tunnel restart; use a new test room/link rather than treating that as same-origin reconnect recovery. A backend restart while keeping the tunnel running preserves the origin and is a separate recovery test.

## Actual-phone acceptance sequence

1. Host stays on its usual connection. Phone turns Wi-Fi off and opens the player link over 5G/mobile data. Join with a test name. Host and phone both show the same player connected; phone shows round-trip samples.
2. Host starts the test round. Phone receives it, selects an answer and waits for Saved. Refresh Chrome: same identity and saved answer, no duplicate points/player.
3. Switch the phone between mobile data and Wi-Fi. Confirm reconnect/state recovery and that the host sees presence recover. Repeat a short airplane-mode interruption. Distinguish temporary disconnection from revoked/expired access.
4. Lock the phone for at least one minute, then unlock and return to Chrome. State resynchronizes without a new identity. If Chrome killed the tab, confirmed answers still restore.
5. Attempt a save during a connection interruption. Observe pending versus Saved honestly. Restore connectivity; the original action is reconciled/retried with no duplicate submission/score. If the stage closed meanwhile, the UI explains that the old action is not accepted rather than submitting it to the new stage.
6. Run `npm run network:restart` on the laptop. It verifies the task's running backend before signalling its launcher, restarts only that backend and preserves the tunnel URL. Both devices reconnect; room is paused, saved answers remain, and the host explicitly resumes. Do not kill PostgreSQL or remove its volume for this test.
7. Open display access separately: read-only current presentation, no host controls. Revoke the test player's access: existing connection ends and refresh cannot silently reclaim by name.
8. Repeat with a second phone or browser profile to check that private answers are not shared. Record OS/Chrome version, connection types, sample count, latency observations and any errors. Redact tokens/content from screenshots or shared reports.

A temporary tunnel interruption is also a useful later drill, but an expired/changing tunnel URL cannot be repaired solely by the game's reconnect logic. Stop feature progression until real-device join, saved state, network switching, sleep and backend restart checks are confirmed or their blocking defects are fixed.


The E2E runner refuses non-test database targets, creates a uniquely named disposable database per invocation, applies reviewed migrations and uses a dedicated compiled test server on port 4173. It drops only its own created database afterward, including failed test runs. The isolated test role needs CREATEDB, as for migration upgrade tests; production roles do not. This prevents startup recovery in one test server from changing another suite's rooms. It uses synthetic identities/answers and isolated browser contexts. Failure traces are ignored local artifacts and may contain short-lived test grants; do not publish them publicly. CI installs Chromium and runs this suite.

## QR joining and dependency footprint

The host screen shows a scannable QR containing only the public origin and room code, plus a readable code and clickable link. QR creation runs locally; no external QR API receives links or credentials. The image has a four-module quiet zone and an accessible text alternative. A failed QR render leaves link/code joining available. A browser test independently decodes the rendered QR and checks its exact destination, including the absence of host/display access tokens.

Use qrcode-generator 2.0.4 as the single zero-runtime-dependency encoder. jsQR 1.4.0 is a zero-dependency development-only decoder for verification; it is not imported by application code. The server's Socket.IO client is a development dependency; controllers retain their required runtime client. Prefer native browser/Node APIs for simple helpers and avoid additional wrappers. Keep vetted auth/network/database foundations, the lockfile, CI checks and advisory scanning. Package counts include development tools and transitive dependencies; minimizing unnecessary packages does not mean disabling the protections the app needs.
